الجزء 2 من 3

Dictionary<TKey, TValue> و HashSet<T>

شرح سينيور لطالب Backend .NET: هنفهم الـ Hashing من الصفر، وإزاي البحث بقى سريع، وإيه الأخطاء اللي بتكلّف في الإنتاج.

1. الفكرة: ليه محتاجين Hash Table؟

لو عندك قائمة فيها مليون مستخدم وعايز تلاقي مستخدم بالـ Id، الـ List<T> هتلف على العناصر واحد واحد (O(n)). الفكرة الذكية: بدل ما تبحث، حوّل الـ Key نفسه لرقم (Hash Code) واستخدم الرقم ده كـ index في Array وروح مباشرة للمكان. النتيجة: بحث بمتوسط O(1) بدل O(n).

لكن مشكلتين لازم التصميم يحلهم:

  1. الـ Hash Code ممكن يكون رقم ضخم (مليارات)، فالـ Array لازم تكون صغيرة ← نأخذ باقي القسمة (modulo) على حجم الـ Array.
  2. مفاتيح مختلفة ممكن تعطي نفس الـ index (Collision) ← لازم طريقة لتخزين أكتر من عنصر في نفس المكان. الـ Collision مش عيب، هو حتمية رياضية (Pigeonhole Principle): لو عندك مفاتيح أكتر من الخانات هتتكرر خانات.

2. Dictionary من جوه (الميكانيزم الحقيقي)

التنفيذ في .NET مبني على مصفوفتين (مبسط):

private int[]   _buckets;   // كل خانة بتشاور على أول Entry في الـ chain (index+1 ، و 0 يعني فاضية)
private Entry[] _entries;   // العناصر نفسها

private struct Entry
{
    public uint   hashCode;
    public int    next;     // index الـ Entry التالية في نفس الـ chain (مش object منفصل)
    public TKey   key;
    public TValue value;
}

البحث خطوة خطوة (dict[key])

  1. حساب hash = comparer.GetHashCode(key).
  2. bucket = hash % _buckets.Length.
  3. الدخول على أول Entry في الـ bucket والمشي على next.
  4. لكل Entry: قارن الـ hashCode أولاً (رخيصة)، ولو اتطابق قارن Equals(key).
  5. لقيتها ← رجّع الـ value. انتهت الـ chain من غير تطابق ← غير موجود.

الملاحظة المهمة: تكلفة البحث = حساب الـ Hash + طول الـ chain. لو الـ Hash موزّع كويس الـ chain فيها عنصر أو اتنين ← O(1). لو كل المفاتيح لها نفس الـ Hash ← الـ chain بتبقى كل العناصر ← O(n).

النمو (Resize)

  • أول Add بيحجز حجم صغير (3 خانات).
  • لما الـ _entries تمتلي، الحجم بيتضاعف تقريباً لأقرب عدد أولي (Prime)، وبيحصل Rehash لكل العناصر (عشان hash % الحجم الجديد مختلف). عملية غالية O(n).
  • ليه أعداد أولية؟ لأن الـ modulo بعدد أولي بيقلل التجمّع لو الـ Hash Codes فيها نمط (مثلاً كلها مضاعفات 4).
  • لو عارف الحجم مقدماً: new Dictionary<int, string>(capacity: 100_000) لتجنب Resizes متكررة (نفس منطق List<T>).

الحذف والترتيب

لما تعمل Remove الخانة بتتحط في Free List وبتتعاد استخدامها مع أول Add جديد. معناها إن ترتيب العناصر عند الـ foreach ممكن يكون هو ترتيب الإدخال في المعتاد، لكن بعد أي حذف بيتغير.

مفاهيم خاطئة شائعة

المفهوم الخاطئ الحقيقة
"البحث في Dictionary دايماً O(1)" O(1) بمتوسط الحالة بشرط Hash جيد. الأسوأ O(n). كمان حساب Hash لـ string طويل نفسه O(طول النص).
"Dictionary مرتبة بترتيب الإدخال" مش مضمون في التوثيق. غالباً بتشتغل كده من غير حذف، لكن متعتمدش عليها.
"الـ chain متكونة من Linked List objects" لأ، الـ chain منظمة بـ indices داخل Array واحدة ← Cache-friendly ومفيش Allocation لكل عنصر.
"أي نوع ممكن يكون Key من غير مشاكل" لازم Equals و GetHashCode متسقين (القسم الجاي).

3. عقد GetHashCode و Equals

الـ Dictionary مابتشوفش محتوى الـ Key مباشرة، هي بتثق في الـ contract ده:

  1. لو a.Equals(b) ← لازم a.GetHashCode() == b.GetHashCode().
  2. الـ Hash Code لنفس الـ object لازم يفضل ثابت طول ما هو داخل الـ Dictionary.
  3. العكس مش شرط: اتنين مختلفين ممكن يكون لهم نفس الـ Hash (Collision).

الخطأ 1: Override لـ Equals من غير GetHashCode

class Point
{
    public int X, Y;
    public override bool Equals(object? o) => o is Point p && p.X == X && p.Y == Y;
    // مفيش GetHashCode ← Warning CS0659
}

var d = new Dictionary<Point, string>();
d[new Point { X = 1, Y = 2 }] = "A";
Console.WriteLine(d.ContainsKey(new Point { X = 1, Y = 2 })); // False غالباً!

ليه؟ الـ GetHashCode الافتراضي مبني على هوية الـ object، فالـ object الجديد هيروح bucket مختلف وماهيقارنش بالـ Equals أصلاً. النتيجة Bug بيظهر كـ "القيمة مش موجودة" رغم إنك مخزّنها.

الحل (الأحدث والأنظف):

record struct Point(int X, int Y);   // Equals و GetHashCode تلقائيين بالقيمة

// أو يدوياً:
class Point2 : IEquatable<Point2>
{
    public int X, Y;
    public bool Equals(Point2? o) => o is not null && X == o.X && Y == o.Y;
    public override bool Equals(object? o) => Equals(o as Point2);
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

نقطة أداء: لو الـ Key هو struct من غير override لـ Equals، الـ CLR بيستخدم ValueType.Equals اللي ممكن يستخدم Reflection + Boxing ← بطيء جداً. اكتب IEquatable<T> دايماً للـ structs اللي هتستخدمها كـ Keys.

الخطأ 2: Key قابل للتعديل (Mutable)

class Key
{
    public int Id;
    public override bool Equals(object? o) => o is Key k && k.Id == Id;
    public override int GetHashCode() => Id;
}

var k = new Key { Id = 1 };
var d = new Dictionary<Key, string> { [k] = "value" };

k.Id = 2;                         // عدّلت الـ Hash بعد التخزين!
Console.WriteLine(d.ContainsKey(k));  // False
Console.WriteLine(d.Count);           // 1 ← العنصر لسه موجود لكن "ضايع"

العنصر فضل في الـ bucket القديم لكن البحث هيروح للجديد. النتيجة Memory Leak بالمعنى الحرفي وقيم ما تقدرش تحذفها. القاعدة: الـ Keys يفضلوا Immutable (string, int, Guid, record, tuple).

Tuple/Record كـ Composite Key

var prices = new Dictionary<(string Country, string Sku), decimal>();
prices[("EG", "A100")] = 250m;
Console.WriteLine(prices[("EG", "A100")]);

ValueTuple بيعمل Equals/GetHashCode تلقائياً بالقيمة، وبدون Allocation لأنه struct.

تنبيهات عن الـ string Keys

  • string.GetHashCode() في .NET Core+ متغير لكل Process (Randomized) ← ما تخزّنوش في DB أو ملف وتتوقع نفس القيمة بعد إعادة التشغيل. السبب: حماية من هجوم Hash DoS (مهاجم يبعت مفاتيح متعمدة لها نفس الـ Hash عشان يحوّل الـ Dictionary لـ O(n) فيخنق السيرفر).
  • الـ Dictionary<string, T> بيبدأ بـ comparer سريع غير عشوائي ولما يلاحظ عدد كبير من الـ Collisions بيتحول لـ Randomized تلقائياً كدفاع.
  • المقارنة الافتراضية Case-Sensitive. للـ Case-Insensitive استخدم StringComparer.OrdinalIgnoreCase (مش ToLower() في كل مرة لأنها بتعمل Allocation وتعاني من مشاكل Culture زي Turkish I).
var headers = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase);
headers["Content-Type"] = "application/json";
Console.WriteLine(headers["content-type"]);   // يشتغل

4. العمليات الأساسية (Common Operations)

var stock = new Dictionary<string, int>();

stock.Add("apple", 10);        // لو الـ Key موجود ← ArgumentException
stock["banana"] = 5;           // Upsert: يضيف أو يحدّث (مفيش Exception)
bool added = stock.TryAdd("apple", 99);   // false لأنه موجود، مفيش Exception ولا تغيير

int a = stock["apple"];                   // لو مش موجود ← KeyNotFoundException
if (stock.TryGetValue("cherry", out int c)) { /* موجود */ }
int safe = stock.GetValueOrDefault("cherry", 0);  // يرجع قيمة افتراضية

bool had = stock.Remove("banana");        // يرجع bool
stock.Remove("apple", out int removed);   // يرجع القيمة المحذوفة كمان

foreach (KeyValuePair<string, int> kv in stock)
    Console.WriteLine($"{kv.Key} = {kv.Value}");

foreach (var key in stock.Keys) { }       // Keys/Values Views حيّة (مش نسخة)

مقارنة: إزاي تجيب قيمة؟

الطريقة لو الـ Key مش موجود عدد مرات حساب الـ Hash متى تستخدمها
dict[key] KeyNotFoundException 1 لما وجود الـ Key شرط مضمون من المنطق
ContainsKey ثم dict[key] يتجنب الخطأ 2 (مرتين) تجنبها، هدر أداء
TryGetValue يرجع false 1 الاختيار الأفضل في الغالب
GetValueOrDefault يرجع default 1 لما تكفيك قيمة افتراضية

ليه الـ Exception مش الـ null؟ لأن الـ Value ممكن تكون int (مالهاش null)، ولو رجّعت 0 مش هتعرف هل هي قيمة حقيقية ولا "مش موجود". لذلك الـ TryXxx pattern جاء كتصميم لاسترجاع النتيجة + الحالة معاً.

التعديل أثناء الـ foreach

  • Add / dict[newKey] = ... أثناء الـ enumeration ← InvalidOperationException.
  • من .NET Core 3.0 الـ Remove والـ Clear مسموحين أثناء الـ foreach من غير ما يتكسر الـ enumerator (بخلاف الـ List).
  • ContainsValue بتمشي على كل العناصر ← O(n). لو محتاج بحث معكوس ابني Dictionary تانية للمعكوس.
  • KeyValuePair هو struct (نسخة)، فتعديل kv.Value مابيغيرش الـ Dictionary. لو الـ Value نفسها كائن (class) تعديل خصائصها بيظهر.

5. أنماط استخدام حقيقية

أ) عدّ التكرارات (Counting)

var counts = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
foreach (var w in words)
{
    counts.TryGetValue(w, out int c);   // c = 0 لو مش موجود
    counts[w] = c + 1;                  // الـ Hash بياتحسب مرتين
}

// النسخة الأسرع (.NET 6+): Hash واحد
using System.Runtime.InteropServices;
foreach (var w in words)
    CollectionsMarshal.GetValueRefOrAddDefault(counts, w, out _)++;

ب) تجميع (Grouping)

var byCustomer = new Dictionary<int, List<Order>>();
foreach (var o in orders)
{
    if (!byCustomer.TryGetValue(o.CustomerId, out var list))
        byCustomer[o.CustomerId] = list = new List<Order>();
    list.Add(o);
}
// بديل أقصر: orders.GroupBy(o => o.CustomerId).ToDictionary(g => g.Key, g => g.ToList());

ج) Lookup بدل البحث المتكرر في List (تحسين O(n²) ← O(n))

// بطيء: كل طلب يبحث في قائمة العملاء
foreach (var o in orders)
    o.Customer = customers.First(c => c.Id == o.CustomerId);

// سريع: نبني Dictionary مرة واحدة
var customerById = customers.ToDictionary(c => c.Id);
foreach (var o in orders)
    o.Customer = customerById[o.CustomerId];

ملاحظة: ToDictionary بترمي ArgumentException لو فيه مفاتيح مكررة في المصدر (مشكلة شائعة مع بيانات غير نظيفة).

د) Cache بسيط ومشكلته الخفية

static readonly Dictionary<int, Product> _cache = new();
static Product Get(int id)
{
    if (!_cache.TryGetValue(id, out var p))
        _cache[id] = p = LoadFromDb(id);   // خطر لو فيه أكتر من ثريد (ASP.NET بيشغّل طلبات متعددة)
    return p;
}

الـ Dictionary مش Thread-Safe، والقراءة مع كتابة في نفس الوقت ممكن تعمل تلف في الهيكل الداخلي (حتى حلقات لا نهائية في الـ chain في حالات نادرة). البديل:

static readonly ConcurrentDictionary<int, Lazy<Product>> _cache = new();
static Product Get(int id) =>
    _cache.GetOrAdd(id, k => new Lazy<Product>(() => LoadFromDb(k))).Value;

ليه Lazy؟ لأن GetOrAdd(key, factory) ممكن تشغّل الـ factory أكتر من مرة لنفس الـ Key لو اتنين ثريدات دخلوا معاً (واحد بس هيتخزّن نتيجته). لو الـ factory ثقيل (DB call) هيظهر النداء مكرر. الـ Lazy<T> بيضمن تنفيذها مرة واحدة.

6. مقارنة الـ Dictionaries

النوع البنية الداخلية البحث الترتيب Thread-Safe متى
Dictionary<K,V> Hash Table O(1) متوسط لا لا الافتراضي في 95% من الحالات
SortedDictionary<K,V> Red-Black Tree O(log n) بالـ Key لا لو محتاج ترتيب دائم مع إدخال/حذف كتير
SortedList<K,V> Arrays مرتبة O(log n) بالـ Key لا إدخال قليل وقراءة كتير، ذاكرة أقل (الإدخال O(n))
ConcurrentDictionary<K,V> Hash مع قفل مقسم O(1) لا نعم وصول من ثريدات متعددة
Hashtable Hash قديم (object) O(1) لا جزئياً تجنبه (Boxing ولا Type Safety)
ImmutableDictionary Tree O(log n) لا نعم (مش بيتغير) لقطات بيانات مشتركة من غير قفل

Trade-off الذاكرة: كل Entry في Dictionary بتكلف حجم الـ Key + Value + 8 bytes (hash و next) + خانة bucket. لو عندك ملايين عنصر صغير ممكن Array مرتبة + BinarySearch توفر ذاكرة.

7. HashSet<T>

الفكرة والتنفيذ

HashSet<T> هي Hash Table بدون Values: بنفس الـ buckets + entries لكن الـ Entry فيها القيمة نفسها فقط. الـ contract بتاع Equals/GetHashCode مطبق بالظبط وكل تحذيرات الـ Keys القابلة للتغيير تنطبق هنا.

الميزة الأساسية: مجموعة عناصر بدون تكرار + Contains بـ O(1) متوسط. المشكلة إنه مفيش Index (set[0] غير موجودة) لأن الترتيب مش مضمون.

العمليات

var set = new HashSet<int> { 1, 2, 3 };

bool a = set.Add(2);        // false: موجود بالفعل، مفيش Exception ولا تكرار
bool b = set.Add(4);        // true
bool c = set.Contains(3);   // true (O(1))
bool d = set.Remove(1);     // true
Console.WriteLine(set.Count);

// أشهر أسلوب: كشف التكرار أثناء المرور
var seen = new HashSet<string>();
foreach (var email in emails)
    if (!seen.Add(email))
        Console.WriteLine($"مكرر: {email}");

عمليات المجموعات (نقطة القوة الحقيقية)

var a = new HashSet<int> { 1, 2, 3, 4 };
var b = new HashSet<int> { 3, 4, 5 };

var union = new HashSet<int>(a); union.UnionWith(b);              // {1,2,3,4,5}
var inter = new HashSet<int>(a); inter.IntersectWith(b);          // {3,4}
var diff  = new HashSet<int>(a); diff.ExceptWith(b);              // {1,2}
var sym   = new HashSet<int>(a); sym.SymmetricExceptWith(b);      // {1,2,5}

bool sub  = new HashSet<int> { 3, 4 }.IsSubsetOf(a);   // true
bool over = a.Overlaps(b);                              // true
bool same = a.SetEquals(new[] { 4, 3, 2, 1 });          // true (الترتيب لا يهم)

تصحيح مهم: الـ UnionWith و IntersectWith و ExceptWith بتعدّل الـ HashSet نفسها (In-place)، مش بترجّع نسخة جديدة. أما الـ LINQ Union/Intersect/Except فبترجّع IEnumerable جديدة مؤجلة التنفيذ.

أمثلة واقعية

// 1) صلاحيات: هل المستخدم عنده كل الصلاحيات المطلوبة؟
var userPerms = new HashSet<string>(user.Permissions, StringComparer.OrdinalIgnoreCase);
bool allowed = required.All(userPerms.Contains);   // أو userPerms.IsSupersetOf(required)

// 2) BFS/DFS: منع زيارة نفس العقدة مرتين (يمنع حلقات لا نهائية)
var visited = new HashSet<int>();
if (visited.Add(node)) { /* أول مرة نزورها */ }

// 3) تشويه التكرار بشكل مؤكد
var uniqueIds = new HashSet<int>(ids).Count;

مقارنة: List مقابل HashSet مقابل SortedSet

الخاصية List<T> HashSet<T> SortedSet<T>
يسمح بالتكرار نعم لا لا
الـ Index نعم لا لا
Contains O(n) O(1) متوسط O(log n)
Add O(1) amortized O(1) متوسط O(log n)
الترتيب ترتيب الإدخال غير مضمون مرتبة دائماً
عمليات المجموعات يدوية موجودة موجودة + Range queries (GetViewBetween)
الذاكرة أقل ما يمكن أعلى (buckets + entries) أعلى (عقد Tree)

حدود ومخاطر

  • لو القائمة صغيرة (أقل من ~10–20 عنصر): List.Contains ممكن تكون أسرع من HashSet بسبب كلفة حساب الـ Hash. القياس (Benchmark) هو الحكم.
  • الـ HashSet مش Thread-Safe. للكتابة المتزامنة استخدم lock أو ConcurrentDictionary<T, byte> أو ImmutableHashSet<T>.
  • الترتيب غير مضمون: لو محتاج تشيل التكرار مع الحفاظ على الترتيب استخدم Distinct() (بتحفظ أول ظهور).
  • الـ Keys القابلة للتعديل نفس مشكلة Dictionary.
  • set.TryGetValue(x, out var actual) مفيد للـ canonicalization (ترجع النسخة المخزّنة نفسها لو عايز تدمج نسخ متكررة من الـ objects).

8. أسئلة وإجابات (اختبر نفسك)

اضغط على أي سؤال لتظهر إجابته. جرّب تجاوب في دماغك الأول.

س1: إيه الفرق بين dict.Add(k, v) و dict[k] = v؟

ج: Add بترمي ArgumentException لو الـ Key موجود. الـ indexer بيعمل Upsert (يضيف أو يستبدل بدون ما يرمي). استخدم Add لما تكرار الـ Key يبقى خطأ في المنطق، وTryAdd لما تبقى حالة طبيعية.

س2: ليه ContainsKey ثم dict[key] هدر أداء؟

ج: لأنها تحسب الـ Hash وتمشي على الـ chain مرتين. TryGetValue بتعملها مرة واحدة وترجع القيمة والحالة معاً.

س3: كتبت كلاس وعملت override لـ Equals بس، واستخدمته كـ Key. إيه اللي هيحصل؟

ج: الـ GetHashCode الافتراضي (مبني على الـ reference) هيخلي المفاتيح المتساوية تروح buckets مختلفة، فالبحث هيفشل رغم وجود القيمة. لازم تعمل override للاثنين بنفس الحقول.

س4: إيه اللي يحصل لو عدّلت حقل داخل في حساب الـ Hash بعد ما الـ Key اتخزّن؟

ج: العنصر يفضل في الـ bucket القديم لكن البحث هيروح للجديد، فالعنصر يبقى "ضايع" (موجود في Count ومانقدرش نوصله أو نحذفه). الحل: Keys غير قابلة للتغيير.

س5: هل تقدر تعتمد على ترتيب العناصر في Dictionary أو HashSet؟

ج: لا. غالباً هيكون ترتيب الإدخال من غير حذف، لكن مش مضمون وهيتغير بعد الحذف (الـ Free List) أو في أي إصدار مستقبلي. لو محتاج ترتيب استخدم SortedDictionary أو رتّب النتيجة بـ OrderBy.

س6: ليه HashSet.Add بترجع bool؟

ج: عشان توفّر عليك الـ Hash التاني: if (!seen.Add(x)) بدل if (seen.Contains(x)) ... else seen.Add(x)، وبكده الفحص والإضافة في عملية واحدة.

س7: الفرق بين set.UnionWith(other) و set.Union(other) (LINQ)؟

ج: الأولى بتعدّل الـ set نفسها (In-place) وماتبترجعش حاجة. التانية بترجع IEnumerable<T> جديدة مؤجلة التنفيذ من غير ما تغير الأصل.

س8: عندك قائمتين في كل واحدة 50,000 Id، وعايز المشتركات. أسرع طريقة؟

ج: ابني HashSet من واحدة واعمل IntersectWith مع التانية: O(n+m). الطريقة الساذجة (loop في loop أو List.Contains) تعمل 2.5 مليار مقارنة.

س9: متى يكون Dictionary اختيار سيئ؟

ج: (1) محتاج ترتيب ← Sorted. (2) محتاج الكتابة من ثريدات ← Concurrent. (3) مجموعة صغيرة جداً ← ممكن List/Array أسرع. (4) Keys بها Hash سيء ← تدهور لـ O(n).

س10: كود بيعمل dict[key] وبيرمي KeyNotFoundException في الإنتاج أحياناً فقط. إيه الأسباب المحتملة؟

ج: Case-Sensitivity ("Abc" مقابل "abc")، مسافات زايدة في النص، قيمة متغيرة من مصدر خارجي، أو Dictionary مشتركة بين ثريدات بتتغير أثناء القراءة. الحل: TryGetValue + معالجة صريحة لحالة الغياب، وComparer مناسب.

9. ملاحظة سينيور إضافية

  • الـ Load Factor والـ Capacity في Dictionary: مش فيه "Load Factor" قابل للضبط زي Java، الـ Resize بيحصل لما الـ entries تمتلي، فالتحكم الوحيد عندك هو تحديد الـ Capacity المبدئية.
  • Hash Quality: لو بتكتب GetHashCode بالإيد استخدم HashCode.Combine(...) مش X ^ Y (الـ XOR بيعمل Collisions كتير لأن (1,2) و (2,1) هيعطوا نفس النتيجة).
  • تحب نتعمق في: (أ) كيف تشتغل ConcurrentDictionary جواها (Lock Striping)، (ب) تعمل Benchmark بـ BenchmarkDotNet للمقارنة بين List وHashSet. قولي أي واحدة تحبها.
