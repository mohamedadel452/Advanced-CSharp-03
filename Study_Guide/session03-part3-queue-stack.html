الجزء 3 من 3

Queue<T> و Stack<T> + خلاصة اختيار الـ Collection

شرح سينيور لطالب Backend .NET: هياكل بتحكم الترتيب بدل الوصول العشوائي، وهي أساس خوارزميات كتير في الشغل الحقيقي.

1. ليه هياكل بترتيب مقيّد؟

Queue و Stack مش أقل قوة من List، هما بيقيّدوا الواجهة عن قصد عشان يضمنوا حاجتين:

  1. وضوح النية: الكود بيقول إنك بتعالج ترتيب معين (الأقدم أولاً / الأحدث أولاً)، ومايقدرش حد يكسر الترتيب بالغلط.
  2. أداء مضمون: العمليات الأساسية كلها O(1) من غير أي زحزحة عناصر، بخلاف List.RemoveAt(0).

2. Queue<T> (FIFO: الأول دخولاً أول خروجاً)

العمليات

var q = new Queue<string>();

q.Enqueue("A");            // إضافة من النهاية
q.Enqueue("B");
q.Enqueue("C");

string first = q.Peek();   // "A" مشاهدة بدون إخراج
string got   = q.Dequeue();// "A" إخراج من البداية
Console.WriteLine(q.Count);// 2

if (q.TryDequeue(out var item)) { /* "B" */ }   // بدون Exception لو فاضية
if (q.TryPeek(out var next))    { /* "C" */ }

bool has = q.Contains("C");  // O(n)
foreach (var s in q) { }     // من الأقدم للأحدث، ولا يخرج العناصر

q.Clear();
q.Dequeue();                 // InvalidOperationException: Queue empty

تنبيه: Dequeue()/Peek() على قائمة فاضية بترمي Exception، ففي المعالجات التي القائمة ممكن تفضى فيها استخدم TryDequeue.

من جوه: Circular Buffer (مش Linked List)

مفهوم خاطئ شائع: "Queue مبنية على Linked List". غلط. هي Array داخلية مع مؤشرين:

private T[] _array;
private int _head;   // مكان أقدم عنصر (اللي هيخرج)
private int _tail;   // مكان الإضافة الجاي
private int _size;

كل Dequeue بيزوّد _head بس (مابيزحزحش حاجة)، ولما المؤشر يوصل نهاية الـ Array يرجع للبداية (wrap-around بالـ modulo). المساحات اللي بتتحرر بالـ Dequeue بتتعاد استخدامها بالـ Enqueue.

ليه التصميم ده؟ لأن البديل البدائي (List.RemoveAt(0)) بيزحزح كل العناصر ← O(n). الـ Circular Buffer بيخلي الـ Enqueue و Dequeue كلهم O(1) مع محافظة على الـ Cache Locality (ذاكرة متصلة) تماماً ما بتفقده الـ LinkedList.

  • لما تمتلي الـ Array بيحصل Resize (تضاعف) ونسخ للعناصر بترتيبها المنطقي (فالـ wrap بيتفك)، نفس منطق List<T> ← Amortized O(1).
  • لو عارف الحجم التقريبي: new Queue<T>(capacity) أو EnsureCapacity(n) (.NET 6+).

باج شهير: استخدام List كـ Queue

var sw = System.Diagnostics.Stopwatch.StartNew();

var list = new List<int>(Enumerable.Range(0, 100_000));
while (list.Count > 0) list.RemoveAt(0);          // O(n) لكل عنصر ← O(n²)
Console.WriteLine($"List : {sw.ElapsedMilliseconds} ms");

sw.Restart();
var q = new Queue<int>(Enumerable.Range(0, 100_000));
while (q.Count > 0) q.Dequeue();                  // O(1) لكل عنصر
Console.WriteLine($"Queue: {sw.ElapsedMilliseconds} ms");

جرّبها: الفرق بيبقى مئات المرات. ده باج حقيقي بيحصل لما حد يعمل "طابور مهام" بـ List.

أمثلة استخدام حقيقية

1) BFS (البحث العرضي): أقصر مسار في Graph غير موزون:

static int ShortestPath(Dictionary<int, List<int>> graph, int start, int target)
{
    var visited = new HashSet<int> { start };
    var queue = new Queue<(int Node, int Dist)>();
    queue.Enqueue((start, 0));

    while (queue.Count > 0)
    {
        var (node, dist) = queue.Dequeue();
        if (node == target) return dist;

        foreach (var next in graph.GetValueOrDefault(node, new List<int>()))
            if (visited.Add(next))                 // منع التكرار والحلقات
                queue.Enqueue((next, dist + 1));
    }
    return -1;   // مش متصل
}

ليه Queue ممتازة هنا؟ لأن FIFO بيضمن إنك تزور كل العقد اللي على بعد 1 قبل اللي على بعد 2، فأول مرة توصل فيها للهدف هي أقصر مسار مضمون.

2) طابور مهام داخل التطبيق:

var jobs = new Queue<Func<Task>>();
jobs.Enqueue(() => SendEmailAsync("a@x.com"));
jobs.Enqueue(() => GenerateReportAsync());

while (jobs.TryDequeue(out var job))
    await job();

المخاطر في الإنتاج

المشكلة السبب الحل
Queue<T> مش Thread-Safe Enqueue و Dequeue متزامنتين ممكن تتلف الـ _head/_tail/_size ConcurrentQueue<T> (Lock-free) أو Channel<T>
قائمة غير محدودة بتكبر للنهاية الـ Producer أسرع من الـ Consumer ← Memory بتزيد حتى OutOfMemoryException Bounded Queue (حد أقصى) + Backpressure
الـ Capacity بتفضل كبيرة بعد الذروة الـ Array مبتصغرش تلقائياً TrimExcess()
محتاج أولويات مش FIFO بس Queue مابتعرفش أهمية العنصر PriorityQueue<TElement,TPriority> (.NET 6+)

Channel<T>: البديل الحديث للـ Producer/Consumer

using System.Threading.Channels;

var channel = Channel.CreateBounded<int>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait   // لو امتلت ← الـ Producer يستنى (Backpressure)
});

// Producer
_ = Task.Run(async () =>
{
    for (int i = 0; i < 1000; i++)
        await channel.Writer.WriteAsync(i);
    channel.Writer.Complete();
});

// Consumer
await foreach (var item in channel.Reader.ReadAllAsync())
    Console.WriteLine(item);

ميزتها على ConcurrentQueue: مابتعملش Busy-Wait ولا Blocking للثريد، بتدعم async/await وحدود السعة.

PriorityQueue<TElement, TPriority> (.NET 6+)

var pq = new PriorityQueue<string, int>();
pq.Enqueue("عادي", 5);
pq.Enqueue("عاجل", 1);
pq.Enqueue("متوسط", 3);

while (pq.TryDequeue(out var task, out var priority))
    Console.WriteLine($"{priority}: {task}");   // 1 ← 3 ← 5 (الأصغر رقماً أولاً)
  • بنيتها Min-Heap: Enqueue/Dequeue = O(log n).
  • مش Stable: العناصر بنفس الأولوية ممكن تخرج بترتيب مختلف عن الإدخال.
  • مفيش Contains ولا تغيير أولوية عنصر موجود (مشكلة لو عايز Dijkstra حرفياً: الحل إضافة نسخة جديدة وتجاهل القديمة لما تخرج).

3. Stack<T> (LIFO: الأخير دخولاً أول خروجاً)

العمليات

var s = new Stack<int>();

s.Push(1);
s.Push(2);
s.Push(3);

int top  = s.Peek();   // 3 (مشاهدة)
int popped = s.Pop();  // 3 (إخراج)
Console.WriteLine(s.Count);   // 2

if (s.TryPop(out var x))  { /* 2 */ }
if (s.TryPeek(out var y)) { /* 1 */ }

s.Pop(); s.Pop();      // التانية هترمي InvalidOperationException (فاضية)

من جوه

Stack<T> هي Array + عداد _size فقط: Push بيكتب في _array[_size++]، Pop بيقلل _size. نفس منطق تضاعف الـ Capacity في List<T>.

مفاهيم خاطئة شائعة (مهم جداً)

خطأ 1: "الـ Stack<T> بتتخزن في ذاكرة الـ Stack". غلط تماماً. الـ Stack<T> الـ Collection كائن عادي على الـ Heap (الـ Array جواها كمان على الـ Heap). اسمها مشتق من السلوك (LIFO) مش من مكان التخزين. الـ Call Stack للثريد شيء مختلف تماماً (ذاكرة محجوزة لكل ثريد، حوالي 1MB افتراضياً على Windows).

خطأ 2: "الـ foreach على Stack بيمشي بترتيب الإدخال". لأ، بيمشي من القمة للقاع:

var s = new Stack<int>();
s.Push(1); s.Push(2); s.Push(3);

foreach (var i in s) Console.Write(i + " ");        // 3 2 1
Console.WriteLine(string.Join(",", s.ToArray()));   // 3,2,1

var s2 = new Stack<int>(new[] { 1, 2, 3 });         // الـ constructor بيعمل Push لكل عنصر بالترتيب
Console.WriteLine(s2.Pop());                        // 3 (مش 1!)

النتيجة العملية: لو حوّلت Stack لـ List بـ ToList() هتحصل على الترتيب المعكوس.

أمثلة استخدام حقيقية

1) التحقق من الأقواس المتوازنة (مثل محلل JSON/التعبيرات):

static bool IsBalanced(string text)
{
    var pairs = new Dictionary<char, char> { [')'] = '(', [']'] = '[', ['}'] = '{' };
    var stack = new Stack<char>();

    foreach (char c in text)
    {
        if (c is '(' or '[' or '{')
            stack.Push(c);
        else if (pairs.TryGetValue(c, out var open))
        {
            if (!stack.TryPop(out var top) || top != open) return false;
        }
    }
    return stack.Count == 0;
}

Console.WriteLine(IsBalanced("{[()]}"));  // True
Console.WriteLine(IsBalanced("{[(])}"));  // False

ليه Stack؟ القوس اللي بتقفله لازم يكون آخر قوس فتحته ← LIFO بالظبط.

2) Undo / Redo (Stackين):

var undo = new Stack<string>();
var redo = new Stack<string>();
string text = "";

void Edit(string newText)
{
    undo.Push(text);
    text = newText;
    redo.Clear();        // أي تعديل جديد يلغي الـ Redo
}
void Undo()
{
    if (undo.TryPop(out var prev)) { redo.Push(text); text = prev; }
}
void Redo()
{
    if (redo.TryPop(out var next)) { undo.Push(text); text = next; }
}

3) DFS (البحث العمودي) بدون Recursion:

static void Dfs(Dictionary<int, List<int>> graph, int start)
{
    var visited = new HashSet<int>();
    var stack = new Stack<int>();
    stack.Push(start);

    while (stack.Count > 0)
    {
        int node = stack.Pop();
        if (!visited.Add(node)) continue;
        Console.WriteLine(node);

        foreach (var next in graph.GetValueOrDefault(node, new List<int>()))
            if (!visited.Contains(next)) stack.Push(next);
    }
}

ليه Stack متصلة بـ StackOverflowException؟

أي دالة بتنادي نفسها (Recursion) بتحجز Stack Frame في الـ Call Stack. لو العمق كبير (شجرة عميقة، ملفات متداخلة، Graph ضخم)، الـ Call Stack بتخلص والـ CLR بيرمي StackOverflowException. المصيبة: الاستثناء ده ماينفعش تمسكه بـ try/catch والـ Process كلها بتوقف. فلو مدخلاتك من مستخدم ممكن تبقى عميقة جداً، حوّل الـ Recursion لـ Loop + Stack<T> صريحة (زي مثال DFS اللي فوق) وكده الذاكرة هتبقى على الـ Heap ومحكومة بحجم الذاكرة المتاحة بدل 1MB.

// خطر: عمق غير محدود
static int Depth(Node n) => n is null ? 0 : 1 + Math.Max(Depth(n.Left), Depth(n.Right));

Thread-Safety

Stack<T> مش Thread-Safe، البديل ConcurrentStack<T> (لكن هام: ترتيب LIFO مع عدة ثريدات مالهوش معنى كتير لأن مين "الأخير" بيتغير باستمرار).

6. أسئلة وإجابات (اختبر نفسك)

اضغط على أي سؤال لتظهر إجابته. جرّب تجاوب في دماغك الأول.

س1: ليه Queue<T> مش مبنية على Linked List؟

ج: الـ Linked List بتعمل Allocation لكل عنصر وبتخسر Cache Locality. الـ Circular Array بتحقق نفس O(1) مع ذاكرة متصلة وGC أخف.

س2: إيه اللي يحصل لو عملت Dequeue() على Queue فاضية؟ وإزاي تتجنبه؟

ج: InvalidOperationException. تتجنبه بـ TryDequeue أو فحص Count > 0. في الكود المتزامن الفحص المنفصل مش كافي (Race Condition) — استخدم ConcurrentQueue.TryDequeue.

س3: إيه ناتج الكود ده؟ 
var s = new Stack<int>(new[] { 10, 20, 30 });
Console.WriteLine(s.Peek());
Console.WriteLine(string.Join(",", s));

ج: 30 ثم 30,20,10. الـ constructor بيعمل Push لكل عنصر بالترتيب فالأخير (30) يبقى القمة، والـ foreach بيبدأ من القمة.

س4: هل Stack<T> الـ Collection هي نفسها الـ Call Stack؟

ج: لا. Stack<T> كائن على الـ Heap بيتحكم فيه المبرمج، الـ Call Stack مساحة محجوزة لكل ثريد بـ Stack Frames للدوال. نفس المبدأ (LIFO) لكن مكان مختلف وحدود مختلفة.

س5: ليه StackOverflowException خطيرة أكتر من أي Exception تاني؟

ج: ماتنفعش تمسكها بـ catch، والـ Process بتموت فوراً. لو المدخلات ممكن تسبب Recursion عميق استخدم Loop + Stack<T> أو حدّ العمق بشكل صريح.

س6: عندك Producer بيبعت 10,000 رسالة في الثانية وConsumer بيعالج 1,000. إيه اللي هيحصل مع Queue غير محدودة؟

ج: الـ Memory هتكبر باستمرار (9,000 عنصر إضافي كل ثانية) حتى يحصل ضغط على الـ GC أو OOM. الحل: Channel.CreateBounded مع FullMode.Wait (Backpressure)، أو زيادة Consumers.

س7: ما الفرق بين Peek و Dequeue/Pop؟

ج: Peek بيشوف العنصر من غير ما يشيله، التانية بتشيله وترجعه.

س8: عايز Queue فيها أولويات ومع ذلك تحافظ على ترتيب الإدخال للعناصر بنفس الأولوية. إزاي؟

ج: PriorityQueue مش Stable، فاستخدم أولوية مركبة (priority, sequenceNumber) من عداد بيزيد مع كل Enqueue.

س9: ليه مش بنستخدم Stack مكان Queue في BFS؟

ج: Stack هتخليك تنزل للعمق أولاً (DFS) فمش هتضمن أقصر مسار. الـ FIFO هو اللي بيخلي الزيارة مستوى مستوى.

س10: اختار الـ Collection المناسبة لـ: (أ) منع معالجة نفس الطلب مرتين، (ب) حفظ سجل آخر 10 عمليات دخول، (ج) تشغيل المهام بترتيب الوصول.

ج: (أ) HashSet<RequestId> (مع تنظيف دوري أو TTL لتجنب نمو لا نهائي). (ب) Queue بحد أقصى 10 (امسح الأقدم بـ Dequeue عند الإضافة) أو Circular Buffer مخصص. (ج) Queue<T> أو Channel<T> لو متزامن.

  • Deque غير موجود مباشرة: .NET مافيهاش هيكل Double-Ended Queue جاهز (إضافة/حذف من الطرفين O(1))، والممكن تستخدم LinkedList<T> أو تبني واحد بالـ Circular Array.
  • قراءة الـ Source Code: افتح مصدر List<T> وDictionary وQueue<T> على source.dot.net — هتلاقي كل اللي اتشرح هنا مكتوب حرفياً.
  • استخدام LINQ مع الـ Collections: كل ما هو IEnumerable بيشتغل مع LINQ، لكن محاذير الـ Deferred Execution والـ Multiple Enumeration لازم تتعلمها بعد السيشن ده.
  • اقتراح للتعمق بعد الملفات الثلاثة: (أ) LINQ والـ Deferred Execution بعمق، (ب) الـ Concurrent Collections والـ Lock Striping، (ج) Span<T> وMemory<T>، (د) تمارين كود شاملة على Collections للتطبيق. قولي تحب نبدأ بأنهي واحد.
