مقدمة Collections و List<T>

شرح سينيور لطالب Backend .NET: نبدأ بالفهم، وبعدها العمق، ومعاهم كود قابل للتجربة وأسئلة بإجاباتها.

1. ليه الـ Collections موجودة أصلاً؟

المشكلة اللي بدأت منها القصة: الـ Array

الـ Array في .NET هي أسرع هيكل بيانات عندك، لكن ليها قيد جوهري: حجمها ثابت وقت الإنشاء. السبب إنها بتتحجز كـ block متصل (contiguous) في الـ Memory. عشان كده الوصول بالـ index بقى سريع جداً (عنوان البداية + index × حجم العنصر). لكن لو عايز تزود عنصر، مفيش مكان مضمون ورا الـ block، فلازم:

  1. تعمل Array جديدة أكبر.
  2. تنسخ كل العناصر القديمة.
  3. ترمي القديمة للـ GC.

الـ Collections اتعملت عشان تخبي الشغل ده وتقدم هياكل بيانات مناسبة لكل سيناريو (ترتيب، بحث سريع، تفرد، FIFO/LIFO).

الجيل الأول: System.Collections (non-generic) والمشكلة اللي حلّها الـ Generics

قبل .NET 2.0 كان فيه ArrayList وHashtable بيخزنوا كل حاجة كـ object. ده معناه مشكلتين حقيقيتين:

using System.Collections;

var list = new ArrayList();
list.Add(42);        // Boxing: الـ int بيتحط في object على الـ Heap (allocation)
list.Add("hello");   // مفيش أي اعتراض من الـ Compiler

int x = (int)list[0];        // Unboxing
int y = (int)list[1];        // InvalidCastException وقت التشغيل (Runtime) مش وقت الـ Compile
  • Boxing/Unboxing: كل value type (int, double, struct) بيتحول لـ object على الـ Heap، يعني allocation + ضغط على الـ GC. في قائمة فيها مليون رقم، ده مليون object زيادة.
  • غياب Type Safety: الخطأ بيظهر في الإنتاج مش وقت الكتابة.

الحل كان الـ Generics (List<T>): الـ Compiler بيتأكد من النوع، ومفيش Boxing.

ليه الـ Generics في .NET أقوى من Java؟

في Java الـ Generics بتتمسح وقت الـ Compile (Type Erasure) والـ List بتبقى List<Object> تحت السطح. في .NET الـ Generics Reified: النوع موجود وقت التشغيل. الـ JIT بيعمل نسخة متخصصة من الكود لكل value type:

النوع اللي بيحصل في الـ JIT
List<int> نسخة كود مخصصة لـ int، التخزين int[] مباشرة، مفيش Boxing
List<double> نسخة تانية مخصصة
List<string> / List<Product> (reference types) نسخة مشتركة واحدة لكل الـ reference types لأن حجم الـ reference ثابت

تصحيح لمفهوم شائع: "استخدام Generics بيبطّأ البرنامج لأنه بيعمل نسخ كتير". غلط، العكس تماماً: ده اللي بيديك سرعة تقترب من الـ Array الخام.

2. شجرة الـ Interfaces (لازم تحفظها كمنطق مش كحروف)

IEnumerable<T>          ← تقدر تعمل foreach (قراءة فقط، تسلسل)
  └─ IReadOnlyCollection<T>  ← + Count
       └─ IReadOnlyList<T>   ← + indexer [i] (قراءة)
  └─ ICollection<T>          ← + Count, Add, Remove, Contains, Clear
       └─ IList<T>           ← + indexer [i] (قراءة وكتابة)، Insert, RemoveAt, IndexOf
الـ Interface بتقدم إيه متى تستخدمه كنوع Parameter / Return
IEnumerable<T> iteration بس الـ Parameter لو هتعمل loop واحد بس. أوسع نوع ممكن.
IReadOnlyList<T> iteration + Count + index الـ Return لو مش عايز المستدعي يعدّل القائمة
ICollection<T> Add / Remove / Count الـ Navigation properties في EF Core
IList<T> كل حاجة بالـ index نادراً، غالباً List<T> أو IReadOnlyList<T> أنسب

القاعدة الصناعية: استقبل أضعف Interface تحتاجه، وارجّع أقوى Interface تقدر تضمنه. الهدف تقليل التزاوج (Coupling) وإخفاء التنفيذ.

Trade-off: لو رجّعت IEnumerable<T> من Method وجواها ماسك List<T>، المستدعي ممكن يعمل Cast لـ List ويعدّل. ولو رجّعت IEnumerable<T> من LINQ Query مؤجل التنفيذ (Deferred Execution)، كل مرة هتعمل فيها foreach الـ Query هيتنفّذ من الأول (ممكن يعني Database round trip تاني!). ده مصدر Bug شائع في الإنتاج.

3. foreach: الميكانيزم الحقيقي

مفهوم خاطئ شائع: "foreach بتشتغل على أي حاجة بتطبق IEnumerable". الحقيقة إن الـ Compiler بيدور على Pattern: أي نوع فيه method اسمها GetEnumerator() بترجّع نوع فيه MoveNext() وCurrent. (ده Duck Typing وقت الـ Compile.) الكود ده:

foreach (var item in list)
    Console.WriteLine(item);

بيتحول تقريباً لـ:

using (var e = list.GetEnumerator())   // List<T>.Enumerator وهو struct
{
    while (e.MoveNext())
    {
        var item = e.Current;
        Console.WriteLine(item);
    }
}

الـ List<T> بيرجّع Enumerator من نوع struct (مش class) عشان مفيش Allocation على الـ Heap في كل foreach. لكن لو تعاملت مع القائمة من خلال IEnumerable<T> الـ struct ده بيتعمله Boxing.

الـ _version: ليه بتيجيلك "Collection was modified"؟

كل List<T> جواها حقل _version بيزيد مع كل عملية بتغيّر الهيكل (Add, Remove, Insert, Clear, Sort...). الـ Enumerator بيحفظ نسخة منه وقت إنشائه، وفي كل MoveNext() بيقارن. لو اختلفوا يرمي InvalidOperationException.

var nums = new List<int> { 1, 2, 3, 4 };

foreach (var n in nums)
{
    if (n % 2 == 0)
        nums.Remove(n);   // InvalidOperationException: Collection was modified
}

ليه اللغة صممتها كده؟ لو سمحت بالتعديل أثناء الـ iteration، الـ Enumerator ممكن يتخطى عناصر أو يكررها بدون ما تحس (لأن الـ indices اتزحزحت). الأمان هنا قيد مقصود: بيحوّل Bug صامت لـ Exception واضح. وانتبه: الـ check ده ليس Thread Safety، هو "best effort" لاكتشاف أخطاء البرمجة فقط.

4 طرق لحذف عناصر أثناء المرور

الطريقة الكود التكلفة / الملاحظة
RemoveAll (الأفضل) nums.RemoveAll(n => n % 2 == 0); O(n) بمرور واحد، بيعمل Compact فعلي، لا يكسر الـ Enumerator
for عكسي for (int i = nums.Count - 1; i >= 0; i--) if (...) nums.RemoveAt(i); الحذف من الآخر بيمنع زحزحة العناصر اللي لسه ماتفحصتش، لكن كل RemoveAt فيه O(n) shift، يعني ممكن يوصل O(n²)
ToList() Copy foreach (var n in nums.ToList()) nums.Remove(n); بيعمل نسخة كاملة (Memory إضافية) + Remove نفسه O(n)
LINQ Where nums = nums.Where(n => n % 2 != 0).ToList(); بيعمل List جديدة، المرجع القديم عند أي حد تاني مش هيتأثر

4. List<T> من جوه: Dynamic Array مش Linked List

مفهوم خاطئ شائع رقم 1: "List هي Linked List". غلط. List<T> هي Array ديناميكية بتشتغل كده تحت السطح (مبسطة):

public class List<T>
{
    private T[] _items;   // الـ Array الحقيقية
    private int _size;    // Count: عدد العناصر المستخدمة فعلاً
    private int _version; // لاكتشاف التعديل أثناء الـ iteration
}

ولو عايز Linked List فعلاً فهي LinkedList<T> (ونادراً بتكسب في الواقع بسبب الـ Cache Locality والـ allocation لكل Node).

Count مقابل Capacity (فخ كبير)

  • Count: عدد العناصر الفعلية.
  • Capacity: حجم الـ Array الداخلية (_items.Length).
var list = new List<int>(10);   // Capacity=10, Count=0
Console.WriteLine(list.Count);  // 0
Console.WriteLine(list[0]);     // ArgumentOutOfRangeException!

ليه؟ الـ indexer بيتحقق من index < _size مش _items.Length. فالمفهوم الخاطئ إن new List<int>(10) بتعمل 10 عناصر زي new int[10]. لأ، هي بتحجز مساحة بس، لكن القائمة فاضية.

استراتيجية النمو (Growth)

var list = new List<int>();
int last = list.Capacity;
Console.WriteLine($"Start: Capacity={last}");

for (int i = 0; i < 100; i++)
{
    list.Add(i);
    if (list.Capacity != last)
    {
        last = list.Capacity;
        Console.WriteLine($"Count={list.Count}, Capacity={last}");
    }
}

الناتج:

Start: Capacity=0
Count=1,   Capacity=4
Count=5,   Capacity=8
Count=9,   Capacity=16
Count=17,  Capacity=32
Count=33,  Capacity=64
Count=65,  Capacity=128

أول Add بيحجز 4، وبعد كده الـ Capacity بتتضاعف كل ما تمتلي. كل مرة بيحصل: Array جديدة + Array.Copy + القديمة تبقى Garbage.

ليه التضاعف مش +1؟ لو زوّدنا واحد واحد، كل Add هيكلف O(n) نسخ، يعني n عملية Add = O(n²). بالتضاعف، مجموع كل النسخ على n عملية بيطلع حوالي 2n، يعني Amortized O(1) لكل Add. دي نفسها فكرة التحليل المُستهلَك (Amortized Analysis): معظم الـ Add رخيصة، وكل فترة واحدة غالية.

الـ Trade-off: الـ Capacity ممكن تضيّع ذاكرة تصل لـ 50% من الحجم. ولو قائمة فيها 33 عنصر، الـ Capacity هتبقى 64.

الأداء في الإنتاج: حدد الـ Capacity مقدماً لو تعرف الحجم

// سيء: ~20 مرة إعادة حجز ونسخ لمليون عنصر
var a = new List<int>();
for (int i = 0; i < 1_000_000; i++) a.Add(i);

// أفضل: حجز واحد
var b = new List<int>(1_000_000);
for (int i = 0; i < 1_000_000; i++) b.Add(i);

مشكلة إضافية: أي Array حجمها 85,000 byte أو أكتر بتتحجز في الـ Large Object Heap (LOH). التضاعف المتكرر بيعمل Arrays كبيرة قصيرة العمر في الـ LOH، والـ LOH بتتنضّف مع Gen 2 GC بس (أغلى)، فبيحصل ضغط وتفتت (Fragmentation) في الـ Memory. لـ List<int> ده بيبدأ عند حوالي 21 ألف عنصر.

  • TrimExcess(): بتقللل الـ Capacity للـ Count (عملية نسخ، استخدمها لما القائمة تستقر ومش هتزيد).
  • Clear(): بتمسح العناصر لكن لا بتقلل الـ Capacity، يعني الذاكرة فاضلة محجوزة.

5. العمليات الأساسية وتكلفتها الحقيقية

العملية التكلفة ليه
list[i] (قراءة/كتابة) O(1) حساب عنوان مباشر في الـ Array
Add(x) O(1) Amortized / O(n) لو حصل Resize ممكن يحصل نسخ
AddRange(c) O(m) m عدد العناصر المضافة
Insert(i, x) O(n) بيزحزح كل اللي بعد i بـ Array.Copy
RemoveAt(i) O(n) بيزحزح اللي بعده لليسار
Remove(x) O(n) بحث (IndexOf) + زحزحة
Contains(x) / IndexOf(x) O(n) Linear Search ومقارنة بـ Equals
Find / FindAll / Exists O(n) Linear بـ Predicate
Sort() O(n log n) Introsort، غير مستقر (Unstable)
BinarySearch O(log n) يشترط القائمة مرتبة بنفس الـ Comparer
Reverse() O(n) بيعدّل القائمة نفسها (in-place)
ToArray() / GetRange O(n) نسخ

الكود الأساسي بالتطبيق

var names = new List<string> { "Ahmed", "Sara", "Omar" };

names.Add("Mona");                       // ... Ahmed, Sara, Omar, Mona
names.AddRange(new[] { "Ali", "Hana" });  // إضافة مجموعة
names.Insert(1, "Youssef");              // يزحزح الباقي
names.Remove("Omar");                    // أول تطابق فقط، ويرجّع bool
names.RemoveAt(0);                       // حذف بالـ index
names.RemoveAll(n => n.StartsWith("S")); // حذف بشرط، ويرجّع عدد المحذوف

bool has = names.Contains("Mona");       // O(n)
int idx = names.IndexOf("Mona");         // -1 لو مش موجود
string? first = names.Find(n => n.Length > 3);       // null (default) لو مفيش
List<string> all = names.FindAll(n => n.Length > 3);
bool any = names.Exists(n => n == "Ali");

names.Sort();                // ترتيب افتراضي (IComparable)
names.Reverse();
string[] arr = names.ToArray();

6. أخطاء حقيقية بتحصل في الإنتاج

الخطأ 1: Contains / Remove على كائنات بدون Equals

class Product { public int Id; public string Name = ""; }

var products = new List<Product> { new Product { Id = 1, Name = "Laptop" } };

Console.WriteLine(products.Contains(new Product { Id = 1 })); // False!

ليه؟ Contains بتستخدم EqualityComparer<T>.Default. للـ reference types من غير override لـ Equals بتقارن الـ reference (هل هما نفس الـ object؟) مش المحتوى. الحلول:

// 1) Record: بيعمل Equals و GetHashCode بالقيمة تلقائياً
record Product(int Id, string Name);

// 2) Predicate صريح (الأوضح في الغالب)
products.Exists(p => p.Id == 1);

ملاحظة: للـ string و int و struct المقارنة بالقيمة، فبتحس إن الأمور تمام وبعدين بتتفاجئ مع الـ classes.

الخطأ 2: النسخ السطحي (Shallow Copy)

var a = new List<Product> { new Product { Id = 1, Name = "A" } };

var alias = a;                      // نفس القائمة بالظبط (reference واحد)
var copy  = new List<Product>(a);   // قائمة جديدة، لكن نفس العناصر

copy[0].Name = "Changed";           // a[0].Name بقى "Changed" كمان!
copy.Add(new Product { Id = 2 });   // a مش اتأثرت (قائمة مختلفة)

الـ copy constructor ينسخ المراجع مش الـ objects. لو عايز Deep Copy لازم تنسخ كل عنصر بنفسك (أو تستخدم Records مع with والـ immutability).

الخطأ 3: Struct داخل List وتعديل العنصر

struct Point { public int X; }

var pts = new List<Point> { new Point { X = 1 } };
// pts[0].X = 5;   // Error CS1612: Cannot modify the return value of 'List<Point>.this[int]'

ليه؟ الـ indexer بيرجّع نسخة من الـ struct (value type) مش reference ليه، فتعديل النسخة ملوش أي معنى، والـ Compiler منعك عشان ماتفتكرش إنك عدّلت الأصل. الحلول:

var p = pts[0]; p.X = 5; pts[0] = p;                   // نسخ ثم إعادة كتابة
System.Runtime.InteropServices.CollectionsMarshal.AsSpan(pts)[0].X = 5; // تعديل في المكان (.NET 5+)

الخطأ 4: Comparer خاطئ في Sort

nums.Sort((a, b) => a - b);   // خطأ خفي: overflow لو a = int.MaxValue و b سالب
nums.Sort((a, b) => a.CompareTo(b)); // الصح

ولو الـ Comparer متناقض (inconsistent) ممكن Sort يرمي InvalidOperationException. كمان Sort غير مستقر (العناصر المتساوية ممكن تتبدل ترتيبها). لو محتاج Stable استخدم LINQ OrderBy(...).ToList() (مستقر لكن بيعمل قائمة جديدة).

الخطأ 5: List.Contains جوه loop (O(n²))

// 10,000 × 10,000 = 100 مليون مقارنة
foreach (var id in requestedIds)
    if (existingIds.Contains(id)) { ... }

// الحل: HashSet (هنشرحه في الجزء 2)
var set = new HashSet<int>(existingIds);
foreach (var id in requestedIds)
    if (set.Contains(id)) { ... }   // O(1) متوسط

الخطأ 6: List مش Thread-Safe

var list = new List<int>();
Parallel.For(0, 100_000, i => list.Add(i));
Console.WriteLine(list.Count);   // غالباً أقل من 100000، أو Exception

ليه؟ Add مكونة من خطوات (تأكد من الـ Capacity، اكتب في _items[_size]، زوّد _size) مش Atomic. ثريدين ممكن يكتبوا في نفس الخانة فتضيع عناصر، أو يحصل Resize في نفس الوقت. الحلول: lock، أو ConcurrentBag<T> / ConcurrentQueue<T>، أو Immutable collections، أو الأفضل تجمع نتائج كل ثريد لوحده وتدمجهم.

7. ملاحظات تصميم الـ API

سيناريو الاختيار ليه
Return من Method IReadOnlyList<T> أو IEnumerable<T> منع التعديل الخارجي
Parameter IEnumerable<T> لو loop واحد مرونة، يقبل Array و List و LINQ
EF Core Navigation ICollection<T> (أو List<T>) EF محتاج Add/Remove
Public API قابلة للتوسع Collection<T> فيها virtual hooks (InsertItem / RemoveItem)
كلاس داخلي (private) List<T> مباشرة أسرع وأبسط

Trade-off: List<T> كـ Return في Public API بيعمل Coupling على تنفيذ معين وبيسمح للمستخدم يعدّل الحالة الداخلية. دي نقطة مهمة في Libraries، أما في Application Code داخلي فمش لازم تبالغ.

9. أسئلة وإجابات (اختبر نفسك)

اضغط على أي سؤال لتظهر إجابته. جرّب تجاوب في دماغك الأول.

س1: القائمة new List<int>(100) فيها كام عنصر؟ وإيه اللي يحصل لو كتبت list[0] = 5؟

ج: Count = 0 وCapacity = 100. الـ list[0] = 5 هترمي ArgumentOutOfRangeException لأن الـ indexer بيتحقق من Count مش من Capacity. لازم Add الأول.

س2: ليه Add بتوصف بـ "Amortized O(1)" مش "O(1)" بس؟

ج: لأن معظم الـ Add بتكتب في خانة فاضية (O(1))، لكن لما الـ Array تمتلي بيحصل Resize + نسخ كل العناصر (O(n)). بسبب التضاعف، الـ Resize نادر، فمتوسط التكلفة لكل Add يفضل ثابت.

س3: إيه الفرق بين var b = a; وvar b = new List<T>(a);؟

ج: الأولى بتنسخ الـ reference فيبقى في قائمة واحدة باسمين. التانية بتعمل قائمة جديدة بنفس العناصر (Shallow Copy): إضافة/حذف في واحدة لا يؤثر في التانية، لكن تعديل خصائص object مشترك (لو class) بيظهر في الاتنين.

س4: ليه foreach بيرمي Exception لو عدّلت القائمة جواه؟ وإزاي تحذف بأمان؟

ج: بسبب الـ _version اللي بيتقارن في MoveNext. الحذف الأمن: RemoveAll(predicate) أو loop عكسي أو بناء قائمة جديدة بـ LINQ.

س5: عندك 5000 عنصر بتعمل عليهم Remove من الأول بشكل متكرر. إيه المشكلة؟

ج: كل RemoveAt(0) بيزحزح باقي العناصر (O(n)) فالمجموع O(n²). لو الاستخدام FIFO استخدم Queue<T> (الجزء 3). ولو محتاج حذف كتير في النص، فكّر في LinkedList<T> (مع تحفظات) أو هيكل مختلف.

س6: products.Contains(new Product { Id = 1 }) بترجّع false رغم وجود Id = 1. ليه؟

ج: الـ class من غير Equals مخصص بيقارن بالمرجع. الحل: Record، أو override لـ Equals/GetHashCode، أو Exists(p => p.Id == 1).

س7: ليه pts[0].X = 5 ممنوعة لما Point تكون struct؟

ج: الـ indexer بيرجّع نسخة، فالتعديل هيضيع. الـ Compiler بيمنع الخطأ ده بـ CS1612.

10. ملاحظة سينيور إضافية

  • Span<T> وCollectionsMarshal.AsSpan(list): بتديك وصول مباشر للـ Array الداخلية بدون نسخ ولا Allocation، مفيدة في الـ Hot Paths، لكن لو عدّلت حجم القائمة (Add) وانت ماسك الـ Span، الـ Span هتفضل تشاور على الـ Array القديمة، وده Bug صامت.
  • تكلفة LINQ: list.Where(...).ToList() على قائمة ضخمة بتعمل Allocation وبتتأخر بسبب delegates؛ في الكود الحساس فكّر في loop عادي.
  • تحب نتعمق في: (أ) الـ Introsort وليه Sort غير مستقر، (ب) الـ Deferred Execution في LINQ، (ج) Span<T>. قولي أي واحدة تحبها.
